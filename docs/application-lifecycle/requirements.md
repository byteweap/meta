# 应用就绪与失败清理

## 背景与目标

本变更为 16 步修复计划的第 4 步。[第 3 步](../gate-authentication/progress.md) 已提交为 `0d0a8a1`。用户于 2026-11-11 确认本步骤，并要求简洁优雅、不做历史版本兼容。

当前 App 在服务启动调用前就解除等待，可能将尚未可用的服务注册出去；启动钩子、注册或注销失败还会跳过后续清理。本步骤让注册依赖明确的服务就绪信号，并统一正常退出和失败退出的清理。

本变更涉及公共接口、生命周期和并发，采用 Level 2；关键流程选择见 [决策记录](decision.md)。

## 范围与行为

- `Server` 增加必需的 `Ready() <-chan struct{}`，服务完成必要初始化和订阅后关闭该通道。`Start` 持续运行到停止或失败；每个应用及其服务实例用于单次生命周期。
- App 等待全部服务就绪后注册，再执行启动后钩子。等待期间响应启动失败、主动停止、父上下文取消和系统退出信号。
- `Start` 使用应用的可取消运行上下文。NATS 订阅在服务端确认后才返回，确认使用现有连接超时作为上限，失败则退订。
- `Stop` 幂等地发出停止请求并立即返回；`Run` 统一执行清理并报告完整结果。钩子中可以请求停止，无需等待自身结束。
- 每次运行只有一个清理入口，依次执行停止前钩子、注销、停止全部配置服务、等待已启动服务退出、停止后钩子。注销适用于已尝试注册的实例，包括注册失败后可能残留的远端状态。任一步失败都继续并合并错误。
- 清理使用保留应用信息、独立于运行取消状态的限时上下文，默认 10 秒，可通过正数 `StopTimeout` 调整。钩子和服务应遵守传入的截止时间。
- Endpoint 或启动前钩子失败时也回收已打开的监听器；网关正常 HTTP 停止不作为错误返回。
- 同步接口说明、README、测试及本步骤追溯记录。

本步骤包含 App 清理所必需的 Gate/Mesh 生命周期同步。第 5 步的处理器 panic 恢复及第 6 步的网关内部资源完整停止和等待仍单独实施。

## 验收标准

| 编号 | 标准 | 验证方式 |
|---|---|---|
| AC-01 | 注册和启动后钩子不会早于全部服务就绪；启动失败或未就绪时停止能够结束等待 | App 生命周期测试 |
| AC-02 | Endpoint、启动钩子、服务启动和注册失败均触发清理 | 失败注入测试和网关提前监听清理测试 |
| AC-03 | 注销、停止或任意停止钩子失败不跳过后续清理，返回值保留各项错误 | `errors.Is` 与调用记录断言 |
| AC-04 | 清理上下文独立、有截止时间且保留 AppInfo；重复停止不重复清理；超时后仍调用停止后钩子 | 取消、并发停止和超时测试 |
| AC-05 | Gate/Mesh 仅在初始化和订阅成功后就绪，正常停止不误报失败 | 服务就绪与停止测试 |
| AC-06 | NATS 订阅返回后可立即从另一连接接收消息，确认失败不会残留订阅 | 本地内嵌 NATS 测试 |
| AC-07 | 相关模块测试、针对性数据竞争检查、全模块构建和独立代码审查通过 | 本地验证及审查记录 |

## 验证边界

App 和服务生命周期通过可控组件替身及本地连接验证，NATS 使用内嵌测试服务。真实注册中心及线上环境不在本步骤验证范围内。超时控制要求业务钩子和自定义服务遵守 context，Go 无法强制终止忽略取消的函数。

实施和证据见 [进度记录](progress.md)。
