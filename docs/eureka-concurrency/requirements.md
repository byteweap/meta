# 第 13 步：Eureka 并发与通知

## 背景与目标

API 的缓存与订阅 map 存在无锁访问，刷新先通知再写入缓存；同服务的订阅互相覆盖，停止一个监听会删除另一个监听，阻塞通知又为每次广播新增协程。客户端原地打乱共享服务器地址，心跳按服务而非实例存储，取消可能持锁阻塞，注销与在途重注册缺少顺序保障。

用户于 2026-11-11 确认第 13 步：缓存和通知一致、多监听者独立、通知非阻塞、客户端请求及心跳并发安全，完成回归、race、独立审查及 Level 2 记录。基线为第 12 步提交 `8445092`。代码简洁优先，不做历史兼容。

## 范围与规则

- 首次、周期及订阅触发的全量刷新由单一循环串行执行，避免旧请求结果覆盖新状态。触发请求可合并，不为每次订阅/通知额外启动刷新协程。
- 刷新成功后先整体替换缓存再通知。成功空结果清空旧节点；失败保留旧快照，未曾成功时向查询方返回真实错误。已有成功快照时可继续读取上次成功结果。
- GetService 等待首轮刷新完成或 context 取消；完整缓存已初始化后，缺少某服务表示正常空列表，不再回源把旧节点填回。服务分组统一大小写规则。
- 每个 watcher 有独立订阅身份和容量为 1 的通知通道；慢消费者只合并通知，不阻塞刷新和其他 watcher。Stop 可并发重复，只移除自身。监听父 context 或 Registry context 取消均释放等待并清理订阅。
- 查询与监听共用实例转换；返回快照独立于缓存。注册为每个 endpoint 复制输入 Metadata，避免不同 endpoint 和调用方共享写入。
- 每次 HTTP 请求使用独立服务器顺序，不修改客户端或调用方的地址切片；重试保留请求内容、底层错误及取消语义。
- 心跳以 `(AppID, InstanceID)` 唯一标识实例，登记完成后再启动任务；重复注册不产生重叠旧任务，旧任务退出不能删除新任务。注销先终止并等待旧心跳/重注册退出，再发送注销请求；同服务不同实例相互独立。
- 已取消的操作在取得实例操作权后仍须检查取消，不得取消现有有效心跳。Registry context 取消后停止后台任务并拒绝新注册，显式注销仍可使用独立的清理 context 完成。
- 注册由客户端直接协调，不依赖可能过期的发现缓存跳过请求，避免注销后重新注册被旧快照吞掉。取消不持全局锁阻塞，网络请求使用 context 和现有 HTTP 超时。

## 边界

保留现有默认刷新和心跳间隔。构造 Registry 要求至少一个服务地址，刷新和心跳间隔必须为正。使用已有 net/http 客户端，无新增外部 SDK、依赖或兼容分支；必要的内部公开方法签名可调整以保留错误和订阅身份。

不重构 endpoint URL 解析、注册字段策略、跨进程注册归属或远端事务。通知代表最新成功快照，可合并且不保证逐个历史状态被消费；失败期间保留旧快照，不提供额外的过期时间策略。网络取消不能保证服务器尚未处理已收到的请求，但本地注销必须等待旧任务退出，避免本地任务在删除后再次注册。注册或注销返回错误时由调用方处理/重试，不自动恢复已经停止的旧心跳。

真实 Eureka 环境未连接；使用本地 HTTP/可控传输及虚拟时间验证。旧真实服务示例测试改为显式 integration 测试，不以本地替身验证代替真实联调。
