# 停止准入后等待一次清理

## 状态与约束

2026-11-11 采用，依据用户已确认的第 6 步范围。需求见 [需求记录](requirements.md)。

## 选择及理由

使用既有生命周期锁保护停止标记与任务登记，通过一个任务计数和完成通道表达真实清理进度。首个 Stop 启动关闭流程，其他 Stop 等待同一个结果，并各自遵守调用方截止时间。超时不提前关闭完成通道，避免把未释放的资源误报为已完成。

Melody.Close 会发起连接关闭，但不会等待断开回调；其握手流程也可能在检查关闭状态之后才注册连接。因此先禁止新准入并关闭已存在的底层连接，迟到连接在连接回调中关闭；所有已准入请求完成后才调用 Melody.Close。相比给整个 WebSocket 请求持锁，这不会阻塞 Stop；也无需修改 Melody 或增加组件接口。

独立资源的无 context 关闭函数并行发起，再统一等待。单个组件阻塞不会阻止其他组件关闭；调用方超时后，不能强制结束的工作继续留在同一次清理中。

等待以组件关闭方法返回为边界。独立审查确认既有 NATS Close 使用异步 Drain，因此本步骤不声明其内部异步工作已完全结束，也不改变组件接口或 NATS 关闭语义。

## 影响

重复 Stop 会等待真实完成并返回最终清理错误。断开时使用独立清理上下文，每次最多 10 秒；停止后的回调同时受首个 Stop 上下文约束。停止时直接关闭 WebSocket 底层连接，重点保证断开回调、解绑和下线通知的完成顺序。
