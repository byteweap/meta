# 网关停止与资源清理

## 背景与目标

本变更为 16 步修复计划的第 6 步。[第 5 步](../message-panic-recovery/progress.md) 已提交为 `80e71d8`。用户于 2026-11-11 确认实施，要求代码简单清晰、不做历史版本兼容。

当前 Gate.Stop 不等待消息循环、订阅关闭或 WebSocket 断开回调；解绑和下线通知沿用可能已取消的运行上下文。服务监听器还可能在停止过程中创建并遗留。本步骤明确停止时的准入、资源释放和等待顺序。

涉及生命周期与并发，采用 Level 2；关键选择见 [决策记录](decision.md)。

## 范围与行为

- 停止开始后拒绝新连接和新后台任务，任务准入与停止标记由同一把锁保护。
- 已准入的 HTTP/WebSocket 请求、Start、消息循环、服务监听创建和监听循环均在完成后才退出等待范围，订阅关闭等待 `Subscription.Close` 返回。迟到的订阅、监听器或连接必须调用关闭。
- 停止时关闭已有 WebSocket 底层连接，迟到连接发现停止标记后直接关闭，不执行绑定。等待全部请求和断开回调结束后，再关闭 Melody 管理器，避免升级与关闭交错遗留连接。
- 断开清理始终使用独立且有期限的上下文。停止后优先使用首个 Stop 的上下文；每次断开清理最多 10 秒，运行上下文的取消不会提前使解绑和下线通知失败。
- 关闭操作在锁外执行；无 context 的独立组件关闭并行发起，避免一个阻塞组件阻止其余资源关闭。清理错误汇总返回。
- 并发及重复 Stop 共享同一次清理和最终结果，每个调用方的 context 独立限制自己的等待；首个 Stop 的 context 同时用于共享关闭操作和停止后的断开清理。超时不提前标记全部清理完成；后台清理可继续，后续 Stop 可以等待真实结果。

本步骤不改变公共组件接口。第 7 步会话所有权与第 8 步发现初始化/重试保持独立。

## 验收标准

| 编号 | 标准 | 验证方式 |
|---|---|---|
| AC-01 | 停止后新连接与新监听任务被拒绝；迟到资源关闭且不绑定或加入缓存 | 准入、迟到握手和 Watch 故障注入测试 |
| AC-02 | 父运行上下文已取消时，解绑及 offline 通知仍获得有效清理上下文 | 真实 WebSocket 与组件替身 |
| AC-03 | Stop 在断开回调、订阅关闭和监听循环结束前不会报告清理完成 | 通道控制阻塞阶段，检查返回顺序 |
| AC-04 | 并发/重复停止只清理一次，错误可追溯；超时后可继续等待最终结果 | 并发停止、错误注入和超时测试 |
| AC-05 | 组件关闭不持状态锁，一个阻塞关闭不妨碍其他组件释放 | 多监听器及锁内状态访问测试 |
| AC-06 | Gate 既有回归、相关 race、21 模块构建及独立审查通过 | 本地验证记录 |

## 验证边界

测试采用本地 WebSocket 和可控组件替身，不连接真实注册中心、Redis 或 NATS。`Watcher.Stop`、`Subscription.Close` 没有 context；Gate 可以限制等待，但不能强制终止不响应停止的实现。Gate 等待关闭方法返回，无法据此保证组件内部异步工作的完成；现有 NATS 适配器的 Close 调用异步 Drain，其底层订阅和回调彻底退出不在本步骤保证范围内。已发生的会话副作用及多节点会话竞争留在第 7 步处理。

实施和证据见 [进度记录](progress.md)。
