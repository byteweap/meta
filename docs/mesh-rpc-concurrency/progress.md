# Mesh 入站 RPC 并发实施记录

[验收范围](requirements.md)对应基线 `8b7e38d`。

## 分发与停服

默认模式继续使用原消息队列。配置 `RPCConcurrency(workers, queueSize)` 后，订阅回调将服务 RPC 直接交给固定 worker 的有界队列。客户端消息和会话事件仍由同一个消息循环处理。队列满时回调直接通过 Broker 发送 503，慢传输可能延迟同一订阅的后续投递。[实现](../../server/mesh/rpc_pool.go) · [配置示例](../../README.md#入站-rpc-并发)

每个 worker 复用自己的回包期限。并发回包浅拷贝请求头再设置状态码和提示，保留调用方元数据，复用请求载荷。停服时先取消运行中的业务上下文，清理阶段关闭队列并等待 worker 及已开始的过载回复。清理协程可以领取尚在排队的请求，独立于忙碌的 worker 完成回包。已过期的请求回复 504，其余有效请求在主动停服时回复 503。[回包实现](../../server/mesh/mesh.go)

## 验证

在单个 Mesh 上，通过订阅回调投递请求，用通道和虚拟时间控制业务执行。覆盖默认顺序、慢 RPC 与客户端及其他 RPC 的隔离、会话事件顺序、并发上限、容量为零、过载拒绝、排队过期、共享只读请求头和停服期间的回包。停服用例还验证调用方超时后可以再次等待，以及传输 panic 时只尝试回包一次。[并发回归](../../server/mesh/rpc_pool_test.go)

根模块和 game 示例模块测试通过。按约定跳过根模块的两项同进程多节点用例。新增并发用例在 GOMAXPROCS 为 1 和 4 时分别运行 100 次通过，整个 Mesh 包运行 3 轮竞态检查通过。Mesh lint 报告 0 项，`make check` 成功构建 21 个模块。

## 自查结果

三项回归在修复前分别复现。零等待队列可能在 Ready 后误拒首请求，运行上下文取消到关闭接收之间可能漏回已投递的 RPC，清理阶段也可能把已过期的排队请求回复成 503。现在执行与排队名额在投递时一并计数，回包完成后归还。关闭接收前的停服拒绝纳入在途回包等待，worker 和清理协程使用同一套出队校验。另有回归验证 Broker 在订阅失败前投递请求时，Mesh 能回复 503 并跳过业务。[单 Mesh 回归](../../server/mesh/rpc_pool_test.go)
