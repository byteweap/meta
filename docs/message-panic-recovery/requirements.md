# 消息处理器 panic 恢复

## 背景与目标

本变更为 16 步修复计划的第 5 步。[第 4 步](../application-lifecycle/progress.md) 已提交为 `9f11c11`。用户于 2026-11-11 确认本步骤，要求代码简单清晰、不做历史兼容。

Gate/Mesh 在消息循环退出的延迟函数中间接调用 `async.Recover`，无法正确捕获消息处理器的 panic；即使在循环外恢复，也不能让已经退出的循环继续处理消息。目标是把恢复边界放到每条消息上，并为 RPC 业务异常返回明确的失败结果。

本步骤改变服务故障处理和 RPC 异常响应行为，采用 Level 2 追溯。沿用现有 `async.Recover` 和 RPC 回复流程，不增加公共接口或依赖。

## 已确认范围与实现

- 在 Gate/Mesh 单条消息入口直接 `defer async.Recover(...)`，记录异常和堆栈，终止当前消息处理，继续处理后续消息。
- 删除消息循环退出函数中的无效嵌套恢复调用，保留订阅关闭逻辑。
- 在 Mesh RPC 业务处理器调用处单独恢复 panic，返回空数据、通用 `Internal Server Error` 提示和 500 状态，再走既有唯一回复出口。
- 回复传输发生 panic 时由消息入口恢复，不额外重试回复，避免重复发送。
- 同步 `Recover` 的调用约束说明、README、回归测试和变更记录。

恢复仅覆盖当前消息 goroutine 内的处理，不回滚业务处理器已完成的外部副作用，也不处理业务自行启动的其他 goroutine。第 6 步网关资源管理仍单独确认和实施。

## 验收标准

| 编号 | 标准 | 验证方式 |
|---|---|---|
| AC-01 | Gate 单条消息发生 panic 后，同一消息循环能处理下一条消息 | 订阅回调和回复组件替身注入 panic |
| AC-02 | Mesh 普通路由及上下线、重连回调发生 panic 后，后续消息仍正常处理 | 真实 Mesh 消息循环测试 |
| AC-03 | RPC 业务处理器 panic 时框架只回复一次 500，提示不泄露异常细节，随后正常 RPC 成功 | 检查回复次数、数据、状态、提示和后续请求 |
| AC-04 | 回复组件 panic 时不重试发送，且后续消息继续处理 | 回复传输故障注入 |
| AC-05 | 现有成功、业务失败和非法请求处理行为不受影响 | Gate/Mesh 完整测试 |
| AC-06 | 异常恢复后停止仍关闭订阅；相关 race、构建和独立代码审查通过 | 关闭观察、针对性 race 和构建检查 |

## 验证边界

新增测试使用实际消息循环和组件替身控制消息、异常与回复，不依赖真实 NATS 或注册中心。真实基础设施和线上环境不在本步骤验证范围。

实施和证据见 [进度记录](progress.md)。
